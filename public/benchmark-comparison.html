Why these numbers are not apples-to-apples — and what we do about it

  • Different harness, same benchmark file. Our IFBench uses Ai2's official task through inspect_ai v0.3.268; vendors run their own scoring plumbing. Constraint checks are verifiable and binary, which limits judge variance, but protocol details still differ.
  • Partial runs are still real scores. Runner caps kill long evals; we harvest every completed sample (all 113 carried scores) and publish the CI instead of hiding the run. The matched first-N sample ordering makes lever-vs-baseline deltas comparable sample-for-sample.
  • No winner declarations on underpowered n. At n=113 the CI half-width is about ±9 points. AIME at n=30 resolves only very large effects. The stats gate in the repo blocks winner claims that the data cannot support.
  • Serving transparency. The shim records the serving id the provider returns for every run. Marketing names are never substituted; discrepancies are recorded, not hidden.

The gap-closing program

  1. Baseline locked — IFBench 47.8 [38.8–56.9] is the reference arm every lever is measured against.
  2. Four levers, one variable at a time — ACI tool design, verification gates, context management, planner/executor routing. Each is dispatched alone, harvested, and gets a delta-with-CI verdict: keep or revert.
  3. Confirm on the hard set — any lever that wins on the primary pair gets a confirmation run on GPQA Diamond before any claim is made.
  4. Everything replayable — dispatch log, raw inspect logs and scorecards live in the public repo; every claim on this page traces to one.
